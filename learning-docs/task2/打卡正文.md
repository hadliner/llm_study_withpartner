# llm-algo-leetcode 推理优化 | 202609 Task2 · 单请求 Decode 与生成策略

打卡档位：4.1 最小打卡（草稿，尚未向课程 Issue 或群内提交）

（1）KV Cache 为什么增长？

Decode 每新增一个 token，每层都会把它的 K、V 追加到历史缓存。等长的一批请求，理论字节数约为 `2 × 层数 L × batch B × KV 头数 Hkv × 头维 D × 当前长度 S × 每元素字节 b`；不同长度则把每个请求的 S 分别求和。这里 B 已经表示同一批次驻留的请求数，不能又把“并发请求数”乘一遍。长度翻倍，所存 token 数大约翻倍；注意力计算会访问历史 token，但缓存本身不保存所有 token 两两组成的注意力矩阵，所以不是按 S² 存储。

（2）KV Cache 压力怎么减？

GQA/MQA 减少要保存的 KV 头数，MLA 改用压缩的潜在表示；代价是模型结构或投影/重建计算发生变化，并非原模型随手切换一个参数。低精度 KV 则减少每个元素的字节数，但要评估量化误差和转换开销。PagedAttention 主要减少预留、碎片带来的浪费，不能把它写成每 token 的 K/V 数量减少；Prefix Cache 复用相同前缀，省去重复计算和重复保存的机会，代价是命中条件、生命周期和容量管理。显存不够时还可以考虑卸载/淘汰，代价是数据搬运或重算。

（3）四种选择策略改变什么？

Greedy 固定取最高分 token；Temperature 在 softmax 前缩放 logits，改变概率分布的尖锐程度但不改变排序；Top-k 只保留最高分的 k 个候选；Top-p 保留累计概率达到阈值的最小候选集合，再归一化抽样。温度升高会让低概率 token 更有机会出现，文字可能更丰富，但偏题和结果波动也可能增加；低温采样也不等于 Greedy。

（4）投机解码怎么理解？

小而快的 draft 先提出几个候选 token，target 集中算出验证概率，按接受概率逐个检查。第一次拒绝时从残差分布采样修正 token 并结束该轮；全接受时还可从 target 的额外位置取 bonus token。草稿负责便宜地“提案”，目标负责把最终生成约束在自己的概率分布上。能否真正更快，还取决于接受率、草稿开销和目标验证成本，不能由 CPU 逻辑测试推断加速比。

本地实验：在 PyCharm/Conda CPU 环境，运行官方提交 `518cc451` 下三份 Notebook 的参考实现与原测试：KV Cache 账本中 S 从 1024 到 2048，估算值由 0.54 GB 到 1.07 GB；4096 长度下 32/8/1 个 KV 头分别约 2.15/0.54/0.07 GB。解码策略的 Temperature、Top-k、Top-p、自回归等检查通过；投机解码的接受、残差修正和 bonus 检查通过。此处是机制与理论账本，不是真实模型显存或 GPU 性能测试，也不是独立完成练习 TODO 的证明。
